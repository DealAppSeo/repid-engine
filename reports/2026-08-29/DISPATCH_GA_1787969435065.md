## EXECUTIVE SUMMARY & ALIGNMENT OF INTENT

The progressive-trust signup flow aims to eliminate visitor friction by allowing zero-barrier interaction while letting users watch their RepID move as they learn. However, this collides with a core database constraint: anonymous builders are created with `earns_repid_rewards: false` [V] because un-verified or un-bound identities must not accrue real, transferable reputation points.

The data contracts defined below resolve this conflict without lying to the user or debasing the real RepID score. By utilizing **explicit approximation properties** (modeled after `effective-authority.ts` [V]) and **shadow-mode metadata routing** (modeled after `repid-update.ts` [V]), we decouple the **provisional score** (visible potential value) from the **earned score** (hardened on-chain value).

## 1. `provisional-repid.v0` — THE SHAPE OF AN UNEARNED SCORE

This schema represents RepID accrued by an anonymous account holding only a session token.

### Data Schema (TypeScript Representation)

```typescript
export type VestingStatus = 
  | 'provisional'    // Accrued, but identity criteria are not yet satisfied
  | 'vested'         // Successfully merged into the earned current_repid
  | 'forfeited'      // Expired, abandoned, or invalidated due to policy violation
  | 'not-applicable'; // Administrative bypass or non-vesting event type

export interface ProvisionalRepIdEvent {
  /** Uniquely identifies this provisional event */
  provisional_event_id: string;
  /** The builder record this event belongs to */
  builder_id: string;
  /** The specific action that triggered the update (matches RepIdUpdateInput['eventType']) */
  event_type: string;
  /** The provisional score delta added by this event */
  provisional_delta: number;
  /** Cumulative provisional score after this event was applied */
  provisional_repid_after: number;
  /** The verified proof level of the account when this event occurred */
  proof_level_at_event: string; 
  /** Vesting rules and criteria specified for this event */
  vesting_eligibility: {
    /** Whether this specific event is eligible to transition to 'vested' status */
    eligible_to_vest: boolean;
    /** The specific property in progressive-identity.v0 that triggers vesting */
    vesting_criteria_property: string; 
    /** The deadline timestamp after which status moves to 'forfeited' if unverified */
    expires_at: string | null;
  };
  /** Status of this provisional event */
  vesting_status: VestingStatus;
  /** Explicit contract caveat: alerts downstream systems that this is an approximation */
  repidIsProvisionalApproximation: true;
}
```

### Database Integration & Hard Constraints

To maintain system integrity, we enforce three structural gates:

1. **The Legacy-Proof Gate (Zero-Delta Ledger Enforcement):**
   * Legacy consumers must never mistake provisional points for earned points. If a query sums the `delta` column in `repid_score_events`, the result must be unmodified.
   * **Mechanism:** When a provisional event is logged to `repid_score_events`, the top-level `delta` column is strictly set to `0`. The actual prospective value is placed in `metadata.provisional_delta` and `metadata.mode = 'provisional'`.
   * On the `builders` table, the `current_repid` column continues to store *only* earned (vested) RepID. A separate column, `provisional_repid`, accumulates active provisional points.

2. **Orthogonal Harmony with `earns_repid_rewards`:**
   * The `earns_repid_rewards` column remains `false` [V] for anonymous signups. It behaves as a **routing switch** for incoming scoring events and an **activation trigger** for vesting.
   * When `earns_repid_rewards` is `false`: all score updates bypass `current_repid`, accrue to `provisional_repid`, and write zero-delta ledger entries tagged as `provisional`.
   * When `earns_repid_rewards` flips to `true` (on upgrade), it triggers a batch-vesting procedure that evaluates pending `provisional` events.

3. **Explicit Pending Defaults:**
   * Vesting is never assumed or set as a default-true. Every provisional score entry is written with `vesting_status: 'provisional'`. It remains in this state until an explicit identity-binding routine evaluates the progressive-identity factors and transitions it.

```
          [ Scoring Event Received ]
                     │
          Is earns_repid_rewards?
          ├───► YES ──► Write to current_repid & repid_score_events (delta = FIXED)
          │
          └───► NO  ──► Write to provisional_repid & repid_score_events (delta = 0, mode = 'provisional')
                             │
                     [ Identity Bound ]
                             │
                      Vesting Trigger
                             ├───► Met Criteria? ──► Move to vested, emit PROVISIONAL_VESTED
                             └───► Expired/Failed? ──► Move to forfeited
```

### Open Questions & Gaps
1. **Granular vs. Atomic Vesting (UNVERIFIED):** Does XC's policy require "all-or-nothing" vesting (the entire provisional bucket vests upon any wallet link), or "factor-specific" vesting (e.g., referral rewards vest only after SMS check, but tutorial rewards vest on email check)?
   * *Resolution Strategy:* Require XC's policy to map specific event types to required identity properties in `vesting_criteria_property`.
2. **Sybil / Farming Mitigation (UNVERIFIED):** Since anonymous accounts are free and easy to create, what prevents a botnet from accumulating provisional rewards and batch-vesting them to fresh wallets?
   * *Resolution Strategy:* Define a maximum cap on `provisional_repid` (e.g., 500 points) and enforce IP/behavioral telemetry limits during anonymous sessions.

## 2. `progressive-identity.v0` — PROOF LEVEL AS DATA

This schema represents what an account has actually proven, ensuring absolute compliance with the operator's promise of non-custodial operations and minimal storage of personal information.

### Data Schema (TypeScript Representation)

```typescript
export type ProofStatus = 
  | 'MEASURED'    // The factor was requested, verified, and successfully passed
  | 'APPROXIMATE' // Inferred through a trusted proxy
  | 'NOT_CHECKED' // The factor was never required or evaluated (distinct from FAILED)
  | 'FAILED';     // The factor was requested but failed validation

export interface IdentityFactor {
  /** The status of this specific factor (Four vocabulary states) */
  status: ProofStatus;
  /** Cryptographically secure proof that validation occurred */
  evidence: {
    /** Timestamp of the validation event */
    proven_at: string | null;
    /** Reference to an on-chain/off-chain EAS (Ethereum Attestation Service) attestation */
    eas_attestation_id: string | null;
    /** One-way salted cryptographic hash of verification inputs (if applicable) */
    verification_hash: string | null;
    /** The system identifier that executed the verification */
    verifier_id: string | null;
    /** Specific warnings or limitations associated with the proof */
    caveat: string | null;
  };
}

export interface ProgressiveIdentityProfile {
  builder_id: string;
  /** Current progressive level of the account */
  proof_level: 'LEVEL_0_TOKEN' | 'LEVEL_1_VERIFIED_EMAIL' | 'LEVEL_2_BOUND_WALLET' | 'LEVEL_3_MFA';
  /** Individual verification factors */
  factors: {
    /** Session token ownership check */
    session_token: IdentityFactor;
    /** Email verification check */
    email_verification: IdentityFactor;
    /** Wallet ownership signature check */
    wallet_binding: IdentityFactor;
    /** Multi-factor authentication check */
    mfa_auth: IdentityFactor;
  };
}
```

### Custody and Privacy Fences (Hard Constraints)

To ensure the system never takes custody of a wallet and never stores un-needed personal identifying information (PII), we establish strict, non-negotiable architectural fences:

1. **Zero-PII Storage (Strict Hashing and Attestation Redirect):**
   * Raw emails, phone numbers, and identity strings are **forbidden** from database fields.
   * Verification must use salted, one-way hashes: `sha256(email_address + user_salt)` or delegate proof validation to EAS. The server only stores the resulting `verification_hash` and `eas_attestation_id`.

2. **Prohibited Fields (The Custody / PII Blacklist):**
   * If any of the following fields are proposed for addition to any database table, it represents a structural violation of our security architecture and must be rejected:
     * `raw_email`, `email_address_text` (Plain text email storage)
     * `raw_phone_number`, `sms_text` (Plain text contact storage)
     * `wallet_private_key`, `wallet_seed_phrase` (Severe custody violation)
     * `oauth_access_token` (Long-lived credentials allowing API impersonation)

3. **Status Differentiation:**
   * The `status` field in each `IdentityFactor` must map to the four-state model. A factor that was never required must be written as `NOT_CHECKED`. It must never share a representation with `FAILED` or a null value that could be misinterpreted as a blank check.

### Open Questions & Gaps
1. **Salt Stewardship (UNVERIFIED):** If we verify email hashes, how do we prevent brute-force dictionary attacks on the hashes in the event of a database dump?
   * *Resolution Strategy:* Utilize a secure environment pepper (stored in AWS Secrets Manager / Railway Secrets, never in the database) combined with the user's `builder_id` as the salt for hashing.
2. **Notification Channel Limitation (UNVERIFIED):** If the system never holds plain-text emails, how can it send out-of-app notifications or alerts?
   * *Resolution Strategy:* Accept that out-of-app notifications are impossible under this architecture. Out-of-app alerts must be handled by an external, privacy-preserving notification network or restricted to in-app notification logs.

## 3. E2E PREDICATES FOR THE NO-WALLET FLOW

To prevent the E2E suite from misreporting configuration gaps or step cascades as deployment failures (such as the `/stake/deposit` 401 error caused by a credential mismatch [V]), we define four structured predicates.

Each predicate is designed to run in order and must explicitly return one of the three runtime states:
- `0` (VERIFIED)
- `2` (NOT_CHECKED)
- `1` / other non-zero (FAILED)

### Predicate 1: Signup Issues Usable Credential (`predicate_signup_credential`)

*   **Goal:** Verifies that `/api/v1/builder/token-signup` is reachable and returns a valid session token and deterministic address.
*   **Evaluation Logic:**
    1. Send `POST /api/v1/builder/token-signup`.
    2. If response status is `404`, return `NOT_CHECKED` (Reason: Endpoint not deployed).
    3. If status is `200` and response body matches `{ ok: true, token: string, builder_address: string, repid_rewards_eligible: false }` [V]:
        * Check that `builder_address` starts with `0xT0KEN` [V] or `0xdead0e707` [V].
        * If validation passes, return `VERIFIED` and cache the credentials in `ctx`.
    4. Otherwise, return `FAILED` with the received HTTP status and error body.

### Predicate 2: Protected Endpoint Accepts Credential (`predicate_credential_acceptance`)

*   **Goal:** Verifies that a protected route accepts the anonymous session token issued in Predicate 1, distinguishing this from a full-account JWT.
*   **Evaluation Logic:**
    1. **Guard check:** If Predicate 1 did not return `VERIFIED`, return `NOT_CHECKED` (Reason: Cascade failure — Predicate 1 failed to issue a credential).
    2. Send `GET /api/v1/builder/dashboard/${ctx.builder_id}` with `Authorization: Bearer ${ctx.token}`.
    3. If response status is `404`, return `NOT_CHECKED` (Reason: Endpoint not deployed).
    4. If response status is `401` or `403`:
        * Inspect body error. If error is `'invalid_session'`, return `FAILED` (Reason: Token was successfully sent but rejected by the server auth middleware).
        * If error is `'no_credential'`, return `FAILED` (Reason: Transport layer failed to attach or forward the token).
    5. If response status is `200` and returns the anonymous dashboard, return `VERIFIED`.
    6. Otherwise, return `FAILED`.

### Predicate 3: Provisional Score Movement (`predicate_provisional_movement`)

*   **Goal:** Verifies that an anonymous learning action successfully increments the builder's `provisional_repid` and records a zero-delta audit log, leaving `current_repid` unchanged.
*   **Evaluation Logic:**
    1. **Guard check:** If Predicate 2 did not return `VERIFIED`, return `NOT_CHECKED` (Reason: Cascade failure — credential is not accepted by protected endpoints).
    2. Retrieve current `current_repid` and `provisional_repid` from dashboard.
    3. Send `POST /api/v1/demo/run-round-anonymous` [V] using the session token.
    4. If response status is `404` or `401`, return `NOT_CHECKED` (Reason: Route not deployed or bypassed).
    5. If status is `400` with `'fleet agents missing'` [V], return `NOT_CHECKED` (Reason: Database seed missing, not a code bug).
    6. If status is `200`:
        * Fetch builder's dashboard again.
        * Assert `current_repid` is exactly equal to its previous value (Real RepID did not move).
        * Assert `provisional_repid` has increased.
        * Query the audit ledger and assert that the new entry has `delta = 0`, `metadata.mode = 'provisional'`, and `metadata.provisional_delta > 0`.
        * If all assertions pass, return `VERIFIED`.
        * If `current_repid` changed, or top-level `delta > 0`, return `FAILED` (Reason: Integrity breach — anonymous interaction leaked into earned RepID!).
    7. Otherwise, return `FAILED`.

### Predicate 4: Vesting on Identity Binding (`predicate_provisional_vesting`)

*   **Goal:** Verifies that converting the account to `earns_repid_rewards: true` via identity binding triggers vesting of provisional points into real RepID.
*   **Evaluation Logic:**
    1. **Guard check:** If Predicate 3 did not return `VERIFIED`, return `NOT_CHECKED` (Reason: Cascade failure — provisional score movement was not verified).
    2. Simulate an identity upgrade (e.g., call `/api/v1/builder/upgrade` or mock-bind a wallet).
    3. If status is `404`, return `NOT_CHECKED` (Reason: Endpoint not deployed).
    4. If status is `200`:
        * Fetch builder's dashboard.
        * Assert `earns_repid_rewards` is now `true`.
        * Assert `current_repid` has increased by the exact amount previously held in `provisional_repid`.
        * Query the audit ledger and assert that a `PROVISIONAL_VESTED` audit entry is recorded with `delta = vested_amount`.
        * Assert `provisional_repid` has been reduced to `0`.
        * If all assertions pass, return `VERIFIED`.
        * If the upgrade succeeded but the score did not transfer, return `FAILED` (Reason: Vesting trigger failure).
    5. Otherwise, return `FAILED`.
