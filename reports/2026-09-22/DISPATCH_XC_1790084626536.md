### 2. Attack the honesty of the reply

**Mechanism ([V]):** `deliver-lib.js:31-83` (`buildReply`).

**Specific attacks examined:**

- **Agent-authored text containing a fence delimiter:** The agent's output is placed inside a single ```` ``` ```` block (`deliver-lib.js:75-77`). A prompt can instruct the model to emit ```` ``` ```` (or `~~~`, `DELIVERED by`, `VERIFIED HERE`, etc.). This breaks the rendered Markdown for a human reader — the claim can leak out of its quarantine or make the VERIFIED section appear to continue into agent text. The separation is therefore **not robust**. A hostile row can cause a reply that a human would read as stronger evidence than it is. (Severity: fails open on quarantine.)

- **`transcripts` detection (`deliver-lib.js:32-36`):** `newLines = after.status.split('\n').filter(...)` where `after.status = git status --porcelain` *after* the run; `transcripts = newLines.filter(l => l.includes('reports/'))`. This is line-containment on the *post-run* porcelain output. A file already dirty before the run (outside `reports/`) would appear in `before.status` and be filtered out of `newLines`, so no transcript is reported even if one appears. The comment in `run-agent.mjs` acknowledges the self-chain deadlock fix (reports/ excluded from dirty check). A hostile agent cannot easily force a false-positive transcript report, but pre-dirty state can suppress a real one. **Does not let an agent cause a falsely-positive "transcript appeared" verdict.**

- **New-file / dirty detection:** Relies on the same before/after line-containment diff. A pre-existing dirty file outside `reports/` keeps the tree "dirty" from the dispatcher's perspective (it refuses on non-reports/ changes), but the reply only flags transcripts. Consistent with the design intent ("agent output must be isolable for review").

- **`ok = run.code === 0 && !run.spawnError` (`deliver-lib.js:62`):** Enumerated exit-0-with-nothing cases that produce a "done" reply:

### 3. The unattended failure modes

**Accumulation ([V] from code):**

The warning is in the job log, not the GitHub branch/PR status or a persistent dashboard. Humans will ignore repeated warnings exactly as the comment fears. The opposite (red on env) would at least surface in the workflow summary. Making yellow impossible to ignore forever without noise requires either a separate "health" metric (e.g. last successful drain timestamp in a dashboard) or escalating the warning to error after N consecutive 2's. As written, a stuck deployment can sit at exit 2 indefinitely while the bridge is effectively off.

**Other accumulation:** Stale `claiming:*` rows from crashes; backlog processing order (priority then age); transcripts pushed to draft PRs on every run that produces one (even blocked).
