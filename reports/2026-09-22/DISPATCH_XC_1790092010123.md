---

### Why this task exists

This repo is about to close its first learning loop. Today an agent marks its own work
`done` and nothing independent ever checks it. The proposed gate is:

1. **Facts in code.** Deterministic, no LLM: did git HEAD move, did the test exit 0,
   does the row exist, did /health return 200, does the transcript sha match.
2. **Judgment by a typed decision model.** One question — "does this evidence support
   this claim?" — answered as a typed value, not prose.
3. **HITL on disagreement or low confidence.** A human on a phone, not another agent.
4. **`done` is never terminal.** Only the verifier writes `verified` / `failed`.

**You are being asked in the window between "designed" and "built", because that is the
only cheap moment.** Once this gate is live it decides which agents earn RepID, and RepID
decides which agents get routed future work. A gate that can be influenced by the worker
it judges does not degrade gracefully — it inverts, and the least honest agent wins.

**3. Fact-gate's own limits (each of the five deterministic checks; all [V] from design + code).**

- **Did git HEAD move?** False positive: attacker force-pushes a commit that advances HEAD but contains no real change (or a commit that touches unrelated files while the claimed work is missing). Or the claimed "work" is a no-op commit.
- **Did the test exit 0?** False positive: vacuous test (early return, flag-guarded `if (false)` path that always passes, or test that checks a proxy like "file exists" instead of behavior). Matches lesson 6 (instrument that cannot return the other answer measures nothing). Brief example: suite that reported "11 passed" on both enabled/disabled runs.
- **Does the row exist?** False positive: row inserted with fabricated data (e.g., a `peer_verification_queue` row claiming "verified" with no corresponding real work, or a status row written by the producer itself). Matches current queue state.
- **Did /health return 200?** False positive: endpoint returns 200 unconditionally or ignores its input/params (health that does not validate the claimed state or artifact).
- **Does the transcript sha match?** False positive: producer writes a transcript whose SHA matches the expected value but whose content is fabricated or empty (or reuses a prior valid transcript). No semantic check of content.

All five have concrete false-positive claims. None is immune; each can be satisfied by a worker that controls the production of the checked artifact without performing the claimed work.

**4. The lease.**

Given columns (no `claimed_at`, no `updated_at`; claim uses `UPDATE ... SET verification_status = 'in_review' WHERE ... IN ('pending', 'in_review')` and accepts re-`in_review`), the minimum change is: add `claimed_at TIMESTAMP WITH TIME ZONE DEFAULT now()` (or `leased_until`) to the table, and change the claim condition to `AND (verification_status IN ('pending') OR (verification_status = 'in_review' AND claimed_at < now() - INTERVAL 'X minutes'))`.

This makes a stale claim reclaimable (after TTL) without making a live claim stealable (live claim keeps its `claimed_at` fresh, so the window never opens for others).

- **TTL too short**: Live verifiers get starved/reclaimed mid-LLM-call or mid-signing/POST; increases "already processed" 409s, wastes work, and can wedge the queue further (more re-claims, more recursion).
- **TTL too long**: Stale `in_review` rows (the current 62k frozen since 2026-07-21) remain unclaimable for a long window; the wedge persists, verifier_agent_id stays NULL, and the learning loop stays broken.
