## Output

**1. The evidence envelope (minimal, forge-resistant set for a verifier with no LLM access)**

- **artifact_hash** (`text` or `bytea`, SHA-256 of the canonical serialized artifact): Proves the exact bytes a verifier can fetch/replay were produced. Does not prove the bytes satisfy any semantic contract, were generated by the claimed producer, or are non-fabricated content (a producer can hash fabricated output).
- **transcript_hash** (`text`, SHA-256 of the full signed prompt+response transcript including model ID, temperature, seed if any, and all tool calls/outputs): Proves the exact context and generation trace. Does not prove the output was correct or that the transcript was not self-generated by the producer.
- **deterministic_probe** (`text`, a fixed challenge string or structured probe derived from the claim, e.g. "Verify: output contains exact substring X from expected_output and matches JSON schema Y"): Proves the producer's output was tested against a concrete, non-prose criterion. Does not prove the probe itself was non-gameable or that the full claim semantics were covered.

The producer controls `claim_text` entirely (can lie or omit); none of the above fields can be forged without breaking the hash or failing the probe. The verifier recomputes hashes/probe on the attached artifact/transcript and rejects on mismatch. This directly satisfies the design constraint: the fact-gate consumes attached evidence, not free-form prose.

**2. Where it goes**

Use the existing `trinity_tasks` columns that already carry exactly this meaning and are already wired to the deterministic verifier leg (`task-verify-leg.ts`, bridge, migrations): `artifact_url` (or `external_artifact_url` when remote), `expected_output` (structured contract/probe), `success_criteria` (human-readable but paired with the above), `verification_method` (`'deterministic-v1'` or `'peer-panel-v1'`), `verified_output` (JSON result of checks), and `proof_of_work` (for the HMAC/transcript binding). 

Do not add a new column or parallel enum. `peer_verification_queue` stays minimal (no artifact/task reference today, as measured); the binding lives on the originating `trinity_tasks` row (already joined in scoring/bridge paths). `requires_external_artifact` can gate whether a hash must be present. This reuses cold-but-complete schema without DDL.

**3. Attack the panel (PEER_VERIFY_PANEL_ENABLED=true, fixed pool `trinity-mel`/`trinity-shofet`/`trinity-gcm`, deterministic round-robin, `computeConsensus` over votes)**

Failures ranked by likelihood/impact of *fabricated work verified* first (the catastrophic direction):

- **Two members share a model/family and fail identically** (e.g. both Groq-hosted Llama variants or correlated blind spots on the same claim class): `computeConsensus` sees 2× same wrong verdict → `verified` (or `disputed`) on fabricated work. Fails toward *fabricated work verified*. (High likelihood; provider hints exist but are hints only.)
- **Producer is itself in the pool** (one of the three claims a task that later routes back to itself via round-robin): Atomic guard in `/respond` blocks self-vote, but if the other two abstain/timeout or the producer spoofs a vote before the guard, or if round-robin assigns it anyway, consensus can form on self-endorsement. Fails toward *fabricated work verified*. (The self-check uses `source_agent_id <> verifierUuid`; it catches direct self but not pool membership.)
- **All votes are abstentions/timeouts** (`decisive.length === 0` → `all_timeout`, `reached: false`): No consensus signal. Producer work is neither verified nor penalized. Fails toward *honest work failed* (or un-scored fabricated work slips through elsewhere). (`computeConsensus` explicitly returns `all_timeout`.)
- **One pool member wedged/dead** (never votes): Only 2 votes possible. If the two agree on fabricated → `verified` (quorum met). If they split or one times out → `no_majority`/`insufficient_votes`. Mixed: can fail either direction, but biased toward fabricated-verified when the live pair colludes/correlates. (Round-robin does not retry dead agents.)
- **Ties** (1 verified + 1 disputed + 1 timeout, or 1-1 with insufficient decisive): `no_majority`, `reached: false`. No verification, no scoring. Fails toward *honest work failed*.

The panel is strong against single malicious verifier but weak against correlated failures in a fixed 3-member pool (exactly the correlated-model and pool-membership cases above). `computeConsensus` is deterministic and correct per its spec; the failure modes are in pool selection and independence.

**5. The unbound HMAC**

`dataToSign = `${queue_id}:${verifier_response_id}:${verdict}`` (no `verifier_agent_id` bound). This permits an attacker who knows a valid `(queue_id, verifier_response_id, verdict)` triple for *any* verifier to replay the exact signature as a *different* verifier_agent_id (the lookup happens after signature check in legacy path; panel path binds agent but HMAC does not cover the name/uuid). A malicious actor with one compromised verifier's secret could forge votes from the other two pool members.

The atomic self-verification guard (`source_agent_id <> verifierUuid` + panel self-check) neutralises direct self-endorsement but does **not** neutralise this: an attacker can still forge a vote from a *different* pool member on a claim they control. The unbound field therefore still permits fabricated work to reach consensus when the attacker controls one pool secret and can replay signatures. It is a real remaining vector (back-compat frozen, as noted).
